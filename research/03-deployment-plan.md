# 03 · Step-by-Step Deployment Plan

This plan is IaC-agnostic. The same ordered steps apply whether you choose Terraform ([04](04-terraform.md)) or CDK ([05](05-aws-cdk.md)). Each step lists _what_ to create; the IaC files in 04/05 show _how_.

## Phase 0 — Prerequisites (one-time, local)

1. **AWS account.** Create one (if new, the 12-month free tier starts now).
2. **IAM admin user.** Create `iam-admin` with `AdministratorAccess`. Generate an access key. Configure locally:
   ```bash
   aws configure --profile linkedin-job
   ```
3. **Region.** Pick one and stick with it. `us-east-1` has the broadest service availability; `eu-west-1` or `eu-central-1` are good if you're in Europe. Set `AWS_REGION` in your shell.
4. **Tooling install:**
   - Docker Desktop
   - AWS CLI v2
   - Either Terraform ≥ 1.6 **or** Node.js 20 + AWS CDK v2 (`npm i -g aws-cdk`)
   - `jq` (handy for shell glue)
5. **Domain (optional).** If you want a real hostname, register one in Route 53 (~$12/yr) or bring your own. Skipping = use the EC2 public DNS + a self-signed cert or HTTP-only for now.

## Phase 1 — Make the app cloud-ready

See [06-app-readiness.md](06-app-readiness.md) for the code-level changes. The non-negotiables:

1. Replace SQLite URL with `postgresql+psycopg://...` driven by env vars.
2. Add `psycopg[binary]` to `requirements.txt`.
3. Run the schema migrations in `app/database.py` against Postgres locally to confirm they're compatible (the `ALTER TABLE` try/except patterns mostly are; verify any SQLite-specific types like `DATETIME` default to `TIMESTAMP` in Postgres).
4. Pull all secrets/config from environment variables — no `.env` shipped in the image.
5. Add a `/health` endpoint that returns 200 once the DB is reachable.
6. Add Cognito OIDC middleware. Protect non-public routes; leave `/health` open.
7. Write a `Dockerfile` (multi-stage, slim base).
8. Build and run locally with a local Postgres + dummy Cognito to confirm it works before shipping.

## Phase 2 — Bootstrap IaC state

Both Terraform and CDK need a place to store state.

### Terraform

```bash
aws s3api create-bucket \
  --bucket linkedin-job-tfstate-<account-id> \
  --region us-east-1
aws s3api put-bucket-versioning \
  --bucket linkedin-job-tfstate-<account-id> \
  --versioning-configuration Status=Enabled
aws dynamodb create-table \
  --table-name linkedin-job-tflock \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST
```

### CDK

```bash
cdk bootstrap aws://<account-id>/us-east-1
```

This creates a `CDKToolkit` CloudFormation stack with an S3 bucket and IAM roles.

## Phase 3 — Network layer

Create:

1. **VPC** `10.0.0.0/16`.
2. **Internet Gateway** + attach.
3. **Public subnet A** `10.0.1.0/24` in AZ-a, with default route to IGW, `map_public_ip_on_launch = true`.
4. **Private subnet A** `10.0.10.0/24` in AZ-a.
5. **Private subnet B** `10.0.11.0/24` in AZ-b — _empty placeholder_ to satisfy RDS's DB subnet group requirement.
6. **DB subnet group** containing the two private subnets.
7. **Security groups:**
   - `sg-web`: ingress 80/443 from `0.0.0.0/0`, egress all.
   - `sg-db`: ingress 5432 from `sg-web` only, egress all.

Verify: nothing else needed (no NAT, no VPC endpoints — at the cost of going via the public IGW).

## Phase 4 — Identity & secrets

1. **Cognito User Pool** with:
   - Email as username, email verification on.
   - Self-sign-up: your call (off if it's a personal app).
   - Hosted UI domain: `linkedin-job-<random>.auth.<region>.amazoncognito.com`.
2. **App client** (confidential, with client secret), callback URL `https://<host>/auth/callback`, logout URL `https://<host>/`.
3. **SSM Parameter Store** SecureStrings:
   - `/linkedin-job/db/url`
   - `/linkedin-job/groq/api_key`
   - `/linkedin-job/cognito/client_secret`
   - `/linkedin-job/cognito/client_id` (regular String)
   - `/linkedin-job/cognito/issuer`
   - `/linkedin-job/session_secret`
4. **IAM roles:**
   - `ecsInstanceRole` — `AmazonEC2ContainerServiceforEC2Role` managed policy (lets the host register with the cluster and pull from ECR).
   - `ecsTaskExecutionRole` — `AmazonECSTaskExecutionRolePolicy` (pulls image, writes logs).
   - `ecsTaskRole` — read access to the SSM parameters above.

## Phase 5 — Database

1. Create the **RDS Postgres** instance:
   - Engine `postgres` v16.
   - Class `db.t3.micro`.
   - Storage 20 GB gp2.
   - Username `linkedin_job`, password generated and stored in the SSM parameter above (or autogenerated by RDS into Secrets Manager).
   - DB subnet group from Phase 3.
   - Security group `sg-db`.
   - `publicly_accessible = false`.
   - Backup retention 7 days.
   - Skip final snapshot for dev; turn on for prod.
2. Wait for `available`.
3. Set `/linkedin-job/db/url` SSM parameter to `postgresql+psycopg://linkedin_job:<pw>@<endpoint>:5432/postgres`.

## Phase 6 — Container image

1. Create ECR repo `linkedin-job/api`.
2. Authenticate Docker:
   ```bash
   aws ecr get-login-password --region $AWS_REGION \
     | docker login --username AWS --password-stdin <account-id>.dkr.ecr.$AWS_REGION.amazonaws.com
   ```
3. Build and push:
   ```bash
   docker build -t linkedin-job/api:0.1.0 .
   docker tag linkedin-job/api:0.1.0 <account-id>.dkr.ecr.$AWS_REGION.amazonaws.com/linkedin-job/api:0.1.0
   docker push <account-id>.dkr.ecr.$AWS_REGION.amazonaws.com/linkedin-job/api:0.1.0
   ```
4. Set up a GitHub Actions workflow later for CI/CD. For now, manual push is fine.

## Phase 7 — ECS cluster + service

1. **ECS cluster** `linkedin-job-cluster` (EC2 launch type).
2. **Launch template** for the container instance:
   - AMI: latest `amazon-ecs-optimized` AL2 (lookup via SSM public parameter `/aws/service/ecs/optimized-ami/amazon-linux-2/recommended`).
   - Instance type: `t3.micro`.
   - IAM instance profile: `ecsInstanceRole`.
   - User data: `echo "ECS_CLUSTER=linkedin-job-cluster" >> /etc/ecs/ecs.config`.
   - Security group: `sg-web`.
   - Subnet: public subnet A.
   - Public IP: yes.
3. **Auto Scaling Group** with min=max=desired=1, attached to the launch template.
4. **Task definition** `linkedin-job-api`:
   - Network mode: `bridge` (simpler) or `awsvpc`.
   - Container: image from ECR, port 8010 → host 80.
   - Env vars wired from SSM parameters (use `secrets` field with `valueFrom = ssm parameter ARN`).
   - Log driver: `awslogs` to log group `/ecs/linkedin-job`.
   - Task role: `ecsTaskRole`, execution role: `ecsTaskExecutionRole`.
5. **ECS service**:
   - Cluster: `linkedin-job-cluster`.
   - Task def: latest revision.
   - Desired count: 1.
   - Deployment: rolling, `maximumPercent=100, minimumHealthyPercent=0` (single host can't do 200%).

## Phase 8 — First run + bootstrap

1. SSH into the EC2 host (key pair on the launch template), confirm `docker ps` shows the API container.
2. Hit `http://<public-ip>/health`. Expect 200.
3. Exec into the container, run any one-time bootstrap (create your initial user in Cognito via console or AWS CLI; create initial `Profile` row via the app).
4. Visit the app: Cognito redirects to hosted UI, sign in, land on dashboard.

## Phase 9 — Scheduler decision

- **A. Stay with in-process APScheduler:** no extra infra. Document that the service must stay at desired count 1.
- **B. Move to EventBridge Scheduler → ECS RunTask:**
  - Create a second task definition `linkedin-job-scrape` with the same image but command `python scripts/run_scrape.py`.
  - Create an EventBridge Scheduler schedule, rate `6 hours`, target `ecs:RunTask` with the scrape task def.
  - Disable APScheduler in the API container (env flag).

Option B is preferred long-term but option A is fine for the free-tier launch.

## Phase 10 — TLS + custom domain (optional)

Cheapest path:

1. Create an ACM cert in your region for `app.example.com`.
2. Create a CloudFront distribution: origin = EC2 public DNS, viewer protocol = redirect-to-HTTPS, cache disabled (or PathPattern-based).
3. Route 53 A/AAAA alias → CloudFront.
4. Update Cognito app client callback to `https://app.example.com/auth/callback`.

This gets you HTTPS without paying for an ALB. CloudFront stays inside its always-free 1 TB/month.

## Phase 11 — Observability + alerts

1. CloudWatch Logs retention on `/ecs/linkedin-job` → 14 days.
2. Billing alarm: SNS topic → email → CloudWatch alarm at $5 estimated charges.
3. Optional CloudWatch dashboard with: EC2 CPU, RDS connections, RDS free storage, ECS service running task count.

## Phase 12 — Teardown / disaster recovery

- `terraform destroy` or `cdk destroy` removes everything **except** the IaC state bucket and the ECR images.
- RDS deletion: take a final snapshot if you might come back.
- Cognito user pool: deleting it loses all users — export first if needed.

## Phase 13 — Day-2 ops checklist

- Rotate Cognito client secret yearly.
- Rotate RDS password (Secrets Manager handles this for free if you switch).
- Rebuild image on a schedule for security patches (base image updates).
- Snapshot RDS before any schema migration.
- Watch the 12-month free-tier expiry date in your AWS billing console.
